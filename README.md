# ProjectMate 로컬 모델 실험 (Qwen3.5 4B LoRA)

ProjectMate의 'AI 변경안' 기능을 GPT 대신 작은 로컬 모델로 할 수 있는지 시험한 기록이다. 앱 운영 모델인 **gpt-6.1-sol**로 학습 데이터를 라벨링하고, 같은 모델과 비교했다(2026-11-19). 제품 기능이 아닌 개인 실험이며, 이 브랜치에는 실험 파일만 있고 운영 코드는 없다.

**한 줄 결론:**
- 4B 모델을 gpt-6.1-sol 라벨 1000건으로 파인튜닝하면, sol 6.1과 결정이 75.8% 일치하고 사례당 약 1.2초에 답한다. sol 6.1은 4.8초다.
- 하지만 실험 전에 정한 판정 규칙으로는 sol 6.1에 비열등하지 않다. 변경 내용(변경 F1)과 새 업무·담당자·마감 같은 세부 변경이 특히 약하다.

## 무엇을 시켰나

입력은 GitHub 이슈·PR 타임라인 원문과 프로젝트의 현재 업무 목록이다. 모델은 세 결정 중 하나를 고르고, 변경을 제안할 때는 바꿀 내용을 JSON으로 낸다.

| 결정 | 뜻 |
|---|---|
| `no_change` | 업무 목록을 바꿀 근거가 없다 |
| `propose_changes` | 완료·상태·담당자·마감 변경이나 새 업무를 제안한다 |
| `needs_clarification` | 사람에게 먼저 확인해야 한다 |

## 사용한 모델과 설정

| 항목 | 내용 |
|---|---|
| 기본 모델 | **Qwen3.5-4B** (`Qwen/Qwen3.5-4B`, Apache-2.0). 장비가 12GB라 bf16 LoRA가 들어가는 4B를 골랐다(9B는 약 22GB 필요) |
| 라벨 모델 | **gpt-6.1-sol** reasoning low. 앱 운영 모델·기본 effort와 같다. 응답을 그대로 학습 정답으로 삼아 따라 하게 했다 |
| 학습 데이터 | 1000건. 학습 대기열 402건, 앞선 학습에서 로컬 모델이 틀린 사례 447건, 같은 분포 추가 151건. 검증 40건. 모두 보류 A와 저장소가 겹치지 않는다 |
| 라벨 분포 | no_change 443, propose_changes 369, needs_clarification 188 |
| 라벨링 비용 | 1040건, 입력 1,905,232 / 출력 138,514 토큰. 실패 0건 |
| 학습 방식 | bf16 LoRA r=16, lr 2e-4, 배치 1×8, 최대 3 epoch, seed 7·8·9 세 번. 검증 손실이 가장 낮은 epoch(세 seed 모두 2)를 시험 전에 골랐다 |
| 학습 장비 | Windows 데스크톱 RTX 4070 12GB. 한 번에 약 50~54분, 최대 VRAM 9.9GiB |
| 서빙 | llama.cpp b12184. GGUF 4비트(Q4_K_M, 2.7GB)와 8비트(Q8_0, 4.6GB) 기본 모델에 LoRA 어댑터(40.5MB)를 올린다. JSON 스키마 강제, temperature 0 |
| 시험지 | 보류 A 253건. 학습에 한 번도 쓰지 않았다 |
| 답안지 1 (GPT) | sol 6.1 low의 보류 A 응답이다. 'sol 6.1처럼 답하는가'를 잰다 |
| 답안지 2 (Claude) | 실험 전에 고정한 Claude 블라인드 라벨이다. 판정 규칙은 이 답안지로 적용한다 |

**지표**
- **결정 일치(G1):** 세 결정 중 같은 것을 고른 비율이다.
- **변경 F1(G2):** 제안한 변경의 (종류, 대상 업무)가 답안지와 겹치는 정도다. 상태 변경은 바꾼 값도 본다.
- **S1:** 하면 안 되는 변경을 낸 사례 수다. 기준은 6건 이하다.
- **S2:** 없는 업무를 참조한 횟수다. 기준은 2건 이하다.

## 결과

### 성능 (보류 A 253건, seed 3회 평균)

| | sol 6.1 답안지 결정 일치 | sol 6.1 답안지 변경 F1 | Claude 답안지 결정 일치 | Claude 답안지 변경 F1 | S1 | 지연 중앙값 |
|---|---:|---:|---:|---:|---:|---:|
| 파인튜닝 전 (4비트) | 45.5% | 35.1% | 42.7% | 29.4% | 57 | 3.2초 |
| **파인튜닝 후 4비트** | **75.8%** | **64.3%** | 66.1% | 50.9% | 6~13 | 1.2초 |
| 파인튜닝 후 8비트 | 75.2% | 62.8% | 65.7% | 51.3% | 6~16 | 1.5초 |
| gpt-6.1-sol low | 100% | 100% | 73.5% | 72.8% | 3 | 4.8초 |

### 알게 된 것

1. **파인튜닝 효과는 확실했다.** sol 6.1 답안지로 결정 일치 +30.3%p, 변경 F1 +29.2%p 올랐다(90% 구간 [+24.2, +36.4], [+23.3, +35.1]). 4비트 기준으로 sol 6.1과의 차이 중 결정 일치 약 56%, 변경 F1 약 45%를 메웠다.
2. **4비트와 8비트는 차이가 없었다.** 8비트 − 4비트는 결정 일치 −0.5 [−2.8, +1.7], 변경 F1 −1.5 [−4.6, +1.7]이다. 지연과 파일 크기로 4비트가 낫다.
3. **학습 한 번의 결과는 크게 흔들린다.** seed만 바꿔도 변경 F1이 최대 5.7%p(61.5~67.2%), S1이 6~16건으로 달라졌다. 그래서 seed 3회 평균으로 비교했다.
4. **'확인 필요'가 가장 약하다.** 라벨의 19%가 확인 필요인데, 로컬은 Claude 답안지의 확인 필요 46건 중 13~16건만 맞혔다. sol 6.1은 22건이다.
5. **세부 변경이 약하다.**
   - sol 6.1이 보류 A에서 낸 새 업무·담당자·마감 변경은 10개다. 로컬은 변형마다 0~2개만 종류와 대상이 맞았다.
   - 맞은 마감 변경도 날짜 값은 틀렸다.
   - 지금 채점은 제목·담당자·마감 값을 보지 않아서 위 점수에는 이 약점이 드러나지 않는다.

### sol 6.1 대비 판정 (Claude 답안지, 마진 −6%p)

판정 규칙은 실험 전에 정했다. 차이(로컬 − sol 6.1)의 90% 구간 하한이 −6%p 이상이면 **비열등**, 상한이 −6%p 미만이면 **미달**, 그 밖은 **판정 불가**다.

| 변형 | 결정 일치 차이 | 변경 F1 차이 | S1 | S2 |
|---|---|---|---:|---:|
| 4비트 seed 7 | −6.3 [−11.1, −1.6] 판정 불가 | −18.5 [−26.2, −11.1] 미달 | 6 | 0 |
| 4비트 seed 8 | −9.5 [−13.8, −4.7] 판정 불가 | −24.3 [−31.8, −16.9] 미달 | 10 | 0 |
| 4비트 seed 9 | −6.3 [−11.1, −1.6] 판정 불가 | −23.1 [−30.3, −16.1] 미달 | 13 | 2 |
| 8비트 seed 7 | −7.5 [−12.3, −2.8] 판정 불가 | −21.5 [−29.5, −13.8] 미달 | 6 | 0 |
| 8비트 seed 8 | −4.7 [−9.9, +0.4] 판정 불가 | −19.2 [−26.5, −11.9] 미달 | 11 | 0 |
| 8비트 seed 9 | −11.1 [−15.8, −6.3] 미달 | −24.0 [−31.4, −16.8] 미달 | 16 | 0 |

- 변경 F1은 모든 변형이 미달이다.
- 금지 변경(S1)은 6개 중 2개만 기준을 통과했다. 없는 업무 참조(S2)는 모두 통과했다.
- 결론적으로 "sol 6.1에 비열등"이라고 쓸 수 없다.

### 혼합 방식: 로컬이 거르고 GPT가 쓴다 (저장된 결과로 계산)

로컬이 `no_change`라고 하면 GPT를 부르지 않는다. 그 밖의 경우에는 sol 6.1 응답을 쓴다.

| Claude 답안지, 6개 변형 평균 | 결정 일치 | 변경 F1 | S1 | S2 | GPT 호출 |
|---|---:|---:|---:|---:|---:|
| 로컬 단독 | 65.9% | 51.1% | 6~16 | 0~2 | 0% |
| 로컬 거르기 + sol 6.1 | 69.8% | 64.1% | **3** | **0** | 37~49% |
| sol 6.1 단독 | 73.5% | 72.8% | 3 | 0 | 100% |

- 금지 변경(S1)과 없는 업무 참조(S2)가 모든 변형에서 기준을 통과했다.
- GPT 호출은 절반 넘게 줄었다.
- 변경 F1은 로컬 단독보다 13%p 오르지만 sol 6.1과는 약 9%p 차이가 남는다. 결정 일치는 약 4%p 낮다.
- 남은 차이는 로컬이 무변경으로 걸러 버린 사례에서 나온다. 그 안에 Claude 답안지의 변경 제안 17~24%, 확인 필요 35~59%가 섞여 있다.
- 6개 중 결정 일치가 비열등인 변형은 1개뿐이고, 변경 F1은 모두 판정 불가이거나 미달이다.
- 저장된 GPT 응답을 다시 쓴 계산이라, GPT를 새로 부를 때의 응답 편차는 빠져 있다.

## 최종 결정

- **앱에는 로컬 모델을 넣지 않는다.** ProjectMate의 AI 변경안은 계속 gpt-6.1-sol로 한다. 이유는 셋이다.
  - sol 6.1 대비 변경 F1이 모든 변형에서 미달이다.
  - 금지 변경이 대부분 기준을 넘었다.
  - 세부 변경 내용이 약하다.
- **가장 쓸모 있어 보이는 구조는 '로컬이 거르고 GPT가 쓰는' 혼합 방식이다.** 다만 실험 기록으로만 남기고 앱에 적용하지 않는다(2026-11-19 결정).
- **서빙은 4비트를 쓴다.** 8비트와 성능 차이가 없고 더 빠르고 작다.

**다시 시작한다면 할 일**
- 혼합 방식에서 무변경 확률에 문턱을 두어 거르는 정확도를 높인다.
- 제목·담당자·마감까지 채점하는 시험 세트를 만든다.
- 보류 A를 여러 번 봤으므로 새 시험지로 다시 확인한다.
- 약한 '확인 필요' 유형의 데이터를 보강한다.
- 9B 모델을 시도한다. 클라우드 GPU가 필요하다.

## 파일 구성

| 경로 | 내용 |
|---|---|
| `REPORT.md` | 실험 보고서. 고정값, 판정 규칙, 라벨링·학습·평가 수치, 해시, 명령 |
| `SETUP-windows.md` | 데스크톱 서빙 환경 준비 |
| `train.py` | LoRA 학습 |
| `make_split.py` | 학습·검증 분할, 학습 데이터 생성, sol 6.1 재라벨링(`--relabel-queue`, `--relabel`) |
| `run.py` | 평가 실행. GPT 평가 스크립트에 로컬 변형과 `sol61-low`를 더했다 |
| `compare.py` | 보류 A 채점, 판정, 짝 부트스트랩 구간 |
| `pool.py` | seed 여러 개의 평균끼리 비교 |
| `hybrid.py` | 혼합 방식 계산 |
| `test_*.py` | 분할·평가 스크립트 테스트 |
| `results/local-*/` | 보류 A 253건에 대한 로컬 모델 응답. 파인튜닝 전 1개, 파인튜닝 후 6개(seed 3 × 4비트·8비트) |
| `evidence/` | 학습 로그, 비교 출력, 서버 확인 기록, 공개하지 않은 파일의 sha256 ([설명](evidence/README.md)) |

- 문서와 스크립트 안의 경로는 원래 저장소 기준이다. 예를 들면 `evals/local-model/...`, `evals/github-timeline-state-change-2026-09-11/...`이다.
- 학습 데이터와 GPT 결과가 없어서 이 브랜치만으로 스크립트를 다시 돌릴 수는 없다.

## 공개하지 않은 것

- **학습 데이터:** 다른 사람의 GitHub 이슈 원문·아이디와 GPT 라벨이 들어 있다.
- **GPT 응답:** sol 6.1의 보류 A 응답(답안지 1)도 같은 이유로 올리지 않았다.
- **LoRA 어댑터 3개:** 각 40.5MB이고, 위 데이터로 학습했다.
- 저장소가 공개라서 올리지 않고 sha256만 `evidence/SHA256SUMS.txt`에 남겼다. 로컬 파일과 `shasum -a 256 <파일>`로 대조할 수 있다.
- 앱(web/)에 붙여 본 실험 코드도 운영 코드를 바꾸지 않으려고 뺐다.
